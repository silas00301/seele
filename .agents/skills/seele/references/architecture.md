# Dendritic architecture map

## Bootstrap and public outputs

`flake.nix` declares inputs and calls `flake-parts.lib.mkFlake` with the recursive module returned by `import-tree ./modules`. Import-tree loads every `.nix` file below `modules/` except paths containing `/_`.

The flake exposes:

- `nixosConfigurations.nerv` for `x86_64-linux`
- `darwinConfigurations.asuka` for `aarch64-darwin`
- `packages.x86_64-linux.default` and `packages.aarch64-darwin.default`, which let plain `nix build` build the native `nerv` or `asuka` system closure
- `packages.<system>.{nixvim,spt-st}` for all four declared Linux/Darwin systems
- `packages.<system>.seele-shell` on Linux, Seele's native Quickshell desktop shell
- `packages.<system>.{seele-greeter,seele-lock,seele-polkit}` on Linux, re-exported from the external shell repository
- `packages.x86_64-linux.{codexbar,t3code-nightly}`, the packaged CodexBar CLI and T3 Code nightly AppImage
- `formatter.<system>` backed by `nixfmt-tree`
- `overlays.zjstatus`
- `modules.<class>.<name>` deferred modules from `flake.modules`
- `darwinPackages`, the `asuka` package set convenience output

`modules/flake/core.nix` enables flake-parts' `flake.modules` support, declares the four systems, owns per-host usernames and the shared Catppuccin values, and configures per-system unstable and stable package sets. `modules/flake/formatter.nix` and `overlays.nix` contribute their outputs independently.

## Deferred modules and active profiles

Feature leaves publish deferred modules through `flake.modules.<class>.<name>`, where class is `homeManager`, `nixos`, or `darwin`. Home Manager profile leaves import named features in activation order. Host and system leaves contribute to these active aggregate profiles:

| Profile | Meaning |
| --- | --- |
| `common` | shared by both hosts |
| `linux` | NixOS-specific |
| `darwin` | macOS-specific |
| `nerv` | host `nerv` only |
| `asuka` | host `asuka` only |

Named modules are available through the flake's `modules` output but remain dormant until a profile or host imports them. Home Manager profiles import user features; system and host aggregates import NixOS and Darwin features such as shells, themes, Homebrew applications, and host-only integrations. This replaces the old behavior where an unlisted file under `home/shared/programs/` was dormant.

`modules/features/` contains program, service, theme, and shared system concerns. `modules/profiles/home/` contains profile-wide Home Manager settings that do not belong to one feature. Raw Nix expressions cannot live directly in the recursive tree; place them below a path containing `/_`.

`modules/features/programs/hypr.nix` owns the active Hyprland configuration and packages its private helpers from `_hypr/`. The screenshot helper combines Hyprland's monitor and visible-window geometry with Slurp so one picker handles window, monitor, and freeform region capture. Hyprpicker holds a frozen frame until Grim captures it; plain captures are saved and copied directly, while the modifier binding hands the same capture to Satty.

## Host assembly

`modules/hosts/nerv.nix` constructs `nixosConfigurations.nerv` from:

1. NixOS `common`, `linux`, and `nerv` deferred modules
2. Catppuccin's and Stylix's NixOS modules
3. Home Manager's NixOS integration
4. Home Manager `common`, `linux`, and `nerv` profiles plus external input modules

Machine configuration and generated hardware settings contribute independently to the NixOS `nerv` profile from `modules/hosts/nerv/`. The host uses NixOS' native Limine module with Secure Boot and the shared Catppuccin theme. Its system profile installs uutils implementations of coreutils, findutils, diffutils, and sed at high priority, so uutils owns overlapping command names while NixOS dependencies and commands absent from uutils retain their GNU implementations.

`modules/features/themes/stylix.nix` supplies the Catppuccin Base16 scheme, the shared Lavender accent, Noto and Maple fonts, and explicit target lists for NixOS, nix-darwin, and Home Manager. Automatic target selection is disabled. Catppuccin keeps the application ports it supports and supplies the Papirus icon theme. Stylix owns Qt and GTK widget themes, Hyprland, Plasma, Zen Browser, Spicetify, X resources, fonts, and nix-darwin's JankyBorders service. Catppuccin's Kvantum and qt5ct modules stay disabled so Qt widgets have one owner, while Stylix's qt5ct and qt6ct settings point to Catppuccin's Papirus icons. Custom Seele Shell, greeter, lock, and polkit components continue to consume the Catppuccin palette directly because neither theming framework has targets for them.

Login is greetd running Seele Greeter, from `modules/features/programs/seele-greeter.nix` (`flake.modules.nixos.seele-greeter`) by way of `modules/hosts/nerv/greetd.nix`. A minimal greeter-only Hyprland instance replaces Cage so Quickshell can use layer shell. The package's `Variants` creates one full-screen `PanelWindow` for every `Quickshell.screen`, while password, PAM message, power-menu, and clock state stay on the shared root. Each output therefore gets the same login state but crops the wallpaper to its own geometry and scale. The wrapper exits the temporary compositor as soon as Quickshell exits, freeing the seat for the authenticated Hyprland session that greetd starts through UWSM. The NixOS UWSM module installs the user units that launch this session and owns `graphical-session.target`; Home Manager's competing Hyprland systemd integration stays disabled. Hyprland desktop services attach to `graphical-session.target`, because the generated `hyprland-session.target` propagates its stop into UWSM and terminates the compositor during startup.

`modules/packages/seele-greeter.nix` wires the external seele-shell flake's `greeter` package into this flake. Its generated system theme carries the declared username and display name, the UWSM session command, the desktop wallpaper, Maple Mono NF CN, and the active Catppuccin palette. The package runs the same seeded grain generator as Seele Shell and applies the shell's 8px radius, translucent panel fill, accent border, vertical wash, grain, and interaction tints to the login and power cards. Its install check runs `qmllint` and asserts that the packaged QML still enumerates screens and paints the grain. A NixOS `system.checks` derivation also asks Hyprland to parse the temporary compositor config during every system build.

`modules/hosts/nerv/sddm.nix` is preserved but dormant: nothing imports `nerv-sddm`, and it carries its own `catppuccin.sddm.enable` so an inactive display manager pulls no theme into the closure and can still come back intact. Two display managers cannot both claim vt1, so restoring one means dropping the other.

The greeter change is invisible to the YubiKey stacks. greetd's PAM service is `auth substack login`, exactly as SDDM's was, so it inherits `login`'s second factor with no entry of its own. Quickshell's Greetd service exposes the IPC `authMessage` fields directly, including whether PAM needs a response, so the greeter submits the pending password only when requested and renders `cue_prompt` with the same key state used by Seele Lock. The Catppuccin SDDM theme could not do this at all because it discarded PAM information messages before they reached the UI.

The same `login` PAM stack explicitly enables `kwallet-pam`. Its early optional Unix pass caches the login password before the final password-and-YubiKey verification, while the PAM session exports the handoff needed to unlock `kdewallet`. greetd opens PAM before the launched session has `XDG_SESSION_TYPE=wayland`, so the stack uses `force_run`; without it, kwallet-pam mistakes this graphical login for a TTY and skips the handoff. Plasma normally starts `pam_kwallet_init` itself, but the Hyprland session has no Plasma session manager, so Seele Greeter installs `plasma-kwallet-pam.service` into `graphical-session.target`. UWSM imports the authenticated login environment before reaching that target, letting the bridge consume the PAM handoff and unlock the wallet without a second prompt.

`modules/features/programs/yubikey.nix` publishes `flake.modules.nixos.yubikey` and owns every PAM surface the key touches; `modules/hosts/nerv/yubikey.nix` only imports it, so a second Linux host adopts the whole scheme — and the existing enrolled keys — by importing the same named module. The split between the two kinds of option matters. `security.pam.u2f.settings` is global — `pam.nix` hands the same attribute set to every service — so `cue` and `cue_prompt` live there; without a cue `pam_u2f` blocks for the touch while printing nothing and the surface reads as hung. `enable` and `control` are per service, and the surfaces fall into two shapes. Approval surfaces — `sudo` and `polkit-1` — keep NixOS' u2f-first order at `sufficient`, so a touch replaces the password; a `sufficient` module placed after `unix` would never be reached. Second-factor surfaces — `login`, which `greetd` substacks, and `seele-lock` — invert that pair through the shared `secondFactor` helper so the password comes first and the touch second.

`secondFactor` sets `unix` to `requisite` and moves u2f to `unix.order + 10` as `sufficient`, so a wrong password short-circuits before anyone is asked for a touch and a successful touch ends the stack ahead of the trailing `pam_deny`. Both must pass, which is the same guarantee as u2f `required` in the opposite order. Use a relative `order` offset, never a constant — NixOS reserves the right to renumber its built-in rules. Note that `unix` names the verifying rule at the end of the stack; `login` also carries an earlier `unix-early` pass that primes the password for `kwallet`, and that one must stay `optional` and stay first.

polkit needs one more thing before a token works there at all, and it is not in the agent. polkit 127 runs its PAM conversation in a socket-activated `polkit-agent-helper@` unit that upstream hardens with `PrivateDevices=yes` and `ProtectHome=yes`, which leaves pam_u2f unable to reach `/dev/hidraw*` or to read the authfile under `~/.config`. It then fails before touching the key and the surface falls back to the password no matter how the agent is written — the dialog still appears and `pam_unix` is still reached, so nothing looks broken. nixpkgs relaxes exactly those three settings, but only under the global `security.pam.u2f.enable`, which this flake keeps off so the module does not attach to `sshd`, `su`, and everything else; `modules/features/programs/yubikey.nix` therefore carries the same relaxation on the unit directly. Note that `sudo` is unaffected and will keep working, which makes this easy to misread as an agent bug. Note also that the touch-detector file is no signal here: pam_u2f builds `/var/run/user/%d/pam-u2f-authpending` from `getuid()`, so under setuid `sudo` it lands in the user's runtime dir but under the root-owned helper it does not.

Seele Polkit is the PolicyKit authentication agent, packaged by the external seele-shell flake and exposed through `modules/packages/seele-polkit.nix`, running as the `seele-polkit` user service in place of hyprpolkitagent. A polkit agent cannot drive PAM itself — polkit owns that conversation through its own setuid helper — so this one uses Quickshell's `Quickshell.Services.Polkit`, where `PolkitAgent` registers with the authority and exposes the live request as `flow`. The reason for replacing hyprpolkitagent is one line in its `CPolkitListener::showInfo`, which printed the message to stdout and never passed it to the UI; `showError` did reach the dialog, so failures were visible but pam_u2f's touch request was not, and `polkit-1`'s `u2f sufficient` looked inert even though the touch worked. Quickshell exposes the same text as `flow.supplementaryMessage`, paired with `supplementaryIsError`, so the cue is drawn next to the password field and the two routes through the stack are both visible. Guard every binding on `flow` being null, because it is null whenever nothing is outstanding. polkit hands over one sentence and no field naming the requester, so the dialog lifts the name out of the message: the clause before " is " is an action's own application name and is drawn in the accent, while polkit's generic "Authentication is required to ..." names nobody and stays plain. That needs `Text.StyledText`, so the message has to be markup-escaped before the span is wrapped around it.

Escalation is pointed at that dialog wherever a caller allows it, and the coverage is deliberately partial. `nh` picks its own elevation program, and its `auto` order tries doas then sudo before run0, so `NH_ELEVATION_STRATEGY=run0` is set for Linux in `modules/features/programs/nh.nix` — as a bare name, so it resolves against the running system rather than pinning one build of systemd into a privilege path. Interactive typing is covered by a fish abbreviation expanding `sudo` to `run0`; an abbreviation and not an alias, because run0 is not argument-compatible with sudo and the rewrite has to be visible before it runs. Note that zsh's `initContent` is just `fish`, so fish is the only interactive shell worth configuring. `nerv` runs sudo-rs rather than sudo, from `modules/hosts/nerv/sudo.nix`; it keeps the `sudo` PAM service name and adds `sudo-i`, so the approval stack applies to both unchanged, and enabling it flips `security.sudo.enable` off by itself because the two cannot coexist. Everything that hardcodes `sudo` internally stays on the terminal prompt, and replacing the binary to change that would break `-u`, `-E`, `-n`, and NOPASSWD callers; the shell's YubiKey OSD is the answer for those instead, built to the same card width, glyph, colour, spacing, and screen position as the dialog — anchoring a layer surface to no edge centres it on the output, which is where the dialog centres its own card so a touch request looks the same wherever it comes from. It is the same card without the password field, since a terminal caller owns its own prompt and only the touch is missing.

`sudo` cannot use that dialog and no amount of agent work changes it: it runs its own PAM conversation on the terminal and offers no hook for a graphical agent. The dialog path for privilege escalation is systemd's `run0`, which authorizes through polkit and therefore lands in this agent with both the key and the password available. It needs no configuration here — `security.polkit.adminIdentities` is `unix-group:wheel`, so the `auth_admin` actions `run0` triggers ask the user to authenticate *as themselves* rather than as root, which is what puts the request on the user's own `u2f_keys`. Do not read `auth_admin` as "authenticate as root" on this host. `sudo` stays installed and unaliased alongside it; aliasing would break `-E`, `-u`, and the non-interactive callers that shell out to it.

Both approval routes are meant to be open at once, which a single PAM stack cannot express: `sudo` and `polkit-1` are byte-identical stacks that run u2f first and block for the touch, so PAM has not asked for a password yet while the key is waiting. The agent closes that gap rather than the stack — the field stays live through the touch window, holds whatever is typed in `pendingPassword`, and flushes it the moment `isResponseRequired` turns true. Do not disable the field on `isResponseRequired`; that is what makes the password look unavailable while the key is pending. Reordering the pair instead would invert the cost, making the password instant and the touch cost a keypress, and was considered and rejected. The dialog takes `WlrKeyboardFocus.Exclusive`, so a password cannot be typed into whatever sits behind it. Its `installCheckPhase` runs `qmllint` against Quickshell's own type definitions, which checks the API usage rather than only the syntax.

Seele Lock's launcher has to reap before it starts. `quickshell -n` exits immediately when an instance for the same config path is already running, and an instance whose lock the compositor refused — because another client still holds `ext-session-lock-v1` — never sees `locked` change, so the `onLockStateChanged` handler that quits it never runs. One such leftover therefore turns every later lock into a silent no-op that polls an idle instance until the readiness loop gives up, and locking stays dead until a rebuild changes the config path and hides the problem. Two guards close it: a watchdog in the QML quits an instance that has not become `secure`, and `lock.sh` runs `quickshell kill -p` on an existing instance first — but only while it reports `unlocked`, because killing a client that holds the lock leaves the compositor locked with nothing alive to unlock it. `Qt.quit()` does terminate a daemonized Quickshell instance; that was verified rather than assumed, so it is not the cause to reach for here.

Seele Lock drives its `seele-lock` PAM service through Quickshell's asynchronous `PamContext`. It submits the password only when PAM requests a response, clears its local copy immediately, and then renders non-interactive PAM messages while pam_u2f waits for the token. The service is declared unconditionally at the system layer because Home Manager cannot create PAM services and an unused PAM file is inert.

The lock screen renders PAM information and errors in its input field. This carries `cue_prompt` onto the lock surface while the desktop shell and its YubiKey OSD sit behind it.

`origin` and `appid` are pinned rather than left to default. A FIDO credential is bound to the relying party it was enrolled under, and pam_u2f derives that from `pam://$HOSTNAME`, so renaming the host orphans every enrolled key — the authenticator answers `FIDO_ERR_NO_CREDENTIALS` and pam_u2f fails on every attempt. Under `sufficient` that failure is invisible, because the password fallback still succeeds; it only surfaces once a stack turns `required`. This flake lost its keys exactly that way when `nerv` was renamed from `pm`. The identity is therefore bound to the flake, `pam://seele`, not to any host: one enrollment covers every Seele host importing the module, and no future rename can invalidate it. Treat the value as enrolled-key state rather than configuration — changing it invalidates every key at once and locks the account out of a `required` stack. Migrate by appending credentials for the new identity before switching, never after: pam_u2f walks every credential on the user's line and skips the ones an authenticator does not recognise, so a file holding both the old and the new binding authenticates under either, which makes the change reversible and leaves no window where nothing works. `pamu2fcfg -n` emits a leading colon and no trailing newline, so it appends onto the existing line rather than starting a new one — but its output is not a valid file on its own, because `-n` suppresses the username. Redirect it with `>` instead of `>>` and the line begins with `:`, pam_u2f finds no entry for the user, and it fails before ever reaching the authenticator: no touch, no `authpending` file, and an instant fallback to the password that looks exactly like the module not being configured at all. Only the first enrollment, which writes the username, may use `>`.

Verify the user mapping and the credential binding together, because they fail independently and the credential check alone will pass on a file whose username is missing: `cut -d: -f1` must equal the login name, and every subsequent colon-separated field is a credential to probe. Field offsets are the same either way, so a probe that starts at field 2 cannot tell the two cases apart.

To verify a credential without a touch, a PAM stack, or a lock screen, replay pam_u2f's own detection probe: `fido2-assert -G -t up=false` over the `keyHandle` from `~/.config/Yubico/u2f_keys` against the origin, which answers `FIDO_ERR_NO_CREDENTIALS` when the binding is wrong. Prefer it to any PAM-level check. `/run/user/$UID/pam-u2f-authpending` proves nothing on its own — the file persists between runs, so its presence is not evidence that the current attempt reached the touch. Note also that an agent shell may run inside a mount namespace where `/etc/pam.d` is bind-mounted from an FHS rootfs rather than the host; `/.host-etc` is then the real `/etc`, and `pamtester` run from that shell tests the wrong stack entirely.

The global `security.pam.u2f.enable` stays off — it would attach the module to `sshd`, `su`, and everything else — so `pkgs.pam_u2f` is installed explicitly for the `pamu2fcfg` that writes the mappings every stack depends on. Enroll a spare key before changing a `control` to `required`: a lost key means recovery through a previous Limine generation.

`modules/hosts/asuka.nix` constructs `darwinConfigurations.asuka` from:

1. Darwin `common`, `darwin`, and `asuka` deferred modules
2. Stylix's nix-darwin module and Home Manager's nix-darwin integration
3. Home Manager `common`, `darwin`, and `asuka` profiles plus external input modules

Machine system settings live in `modules/hosts/asuka/system.nix`. JankyBorders is a nix-darwin service so Stylix can supply its active and inactive colors. The same constructor exports `darwinPackages`.

## Arguments and package sets

Host constructors select `seele.hosts.<name>.username` and pass all flake inputs plus:

- the selected `username`
- `currentSystem`
- `selfPackages`
- `catppuccin`
- `self-path`
- Home Manager-only `pkgs-stable` and `configName`

The per-system `pkgs` set uses unstable nixpkgs, the repository overlays, unfree packages, and the repository's insecure-package exception. `pkgs-stable` selects the stable Linux or Darwin input according to the target system. Reuse these arguments rather than importing nixpkgs inside feature modules.

## Packages and assets

`modules/packages/seele-lock.nix` wires the external seele-shell flake's Linux-only `lock` package into this flake. Its small Quickshell configuration lives in the external repository's `lock/` directory and acquires `ext-session-lock-v1` directly through `WlSessionLock`, with one surface per output. The wrapper rejects duplicate clients and waits for the lock's `secure` signal, so suspend does not proceed until the compositor confirms that every output is covered. Quickshell's native PAM bridge drives the `seele-lock` stack without passing passwords through a command line. The surface shares Seele Shell's generated theme and wallpaper, renders password, failure, and YubiKey prompts in place, and keeps the session actions behind one power menu.

The external lock package copies the shell's material token block rather than maintaining a parallel auth theme: the wallpaper stays unblurred, while the profile marker, power trigger, and power popup use the same 8px geometry, translucent fill, accent border, wash, grain, and interaction tints. The external lock package generates its grain tile from the shell's seeded script during the build, so both packages use the same reproducible texture without committing a binary asset.

The lock's surface component is instantiated once per output by `WlSessionLock`; password text and power-menu state live on the shared root so those instances stay mirrored. Each surface has an enlarged circular profile marker and one bottom-left power button that opens the same six-action grid as Seele Shell's menu-bar Power entry. While the lock owns PAM it writes `seele-lock.state` below `XDG_RUNTIME_DIR`; Seele Shell watches that file and suppresses its duplicate YubiKey OSD, so no hidden prompt survives into the unlocked session.

`modules/packages/codexbar.nix`, `nixvim.nix`, `seele-shell.nix`, `spt-st.nix`, and `t3code.nix` contribute `perSystem.packages`. CodexBar and T3 Code's nightly AppImage are available only on `x86_64-linux`; Seele Shell is available on Linux; their host features consume them through `selfPackages`. The non-flake `t3code-nightly-release` input locks GitHub's latest release metadata, including the AppImage digest, so `nix flake update` advances the nightly without a separately maintained version or hash. Seele Shell is packaged from the external `github:silas00301/seele-shell` input and built on upstream Quickshell. Its AI cockpit normalizes CodexBar data for every configured subscription, refreshes one 365-day scan each minute, derives matching token and cost totals for day, rolling week, rolling month, and all available local history, retries a partial Claude cost response when CodexBar reports tokens with zero cost, and launches the host's managed Pi, OpenCode, Codex, and Claude Code packages through explicit paths. Every harness publishes lifecycle state into `$XDG_STATE_HOME/seele-shell/agents/`, and `seele-control` resolves the records per agent in a fixed order: native records first, then the launcher's CPU wrapper, then raw CPU samples. Pi and OpenCode publish natively from the extensions the Home Manager profile installs — Pi through `agent_start`/`agent_settled`, OpenCode through `session.status` plus permission events. Claude Code and Codex have no extension API but expose the same five lifecycle events, so `flake.modules.nixos.seele-shell-agent-status` configures both at the system layer, where they cannot collide with the mutable config those tools write for themselves: a drop-in under `/etc/claude-code/managed-settings.d`, whose hook arrays Claude Code concatenates with the user's own, and `[hooks]` in `/etc/codex/requirements.toml`, which Codex trusts without the review prompt that gates user and project hooks. Session start, stop, and permission events report waiting, prompt submission reports working, and session end deletes the record. Both call `seele-agent-hook`, which walks up the process tree to record the owning harness pid, because a hook is a short-lived child of the session it describes. Harnesses started outside all of this are still read from subtree CPU usage: a session that stays quiet for twenty seconds is waiting for input. Per-process records allow concurrent sessions; records whose process is gone report a finished run for five minutes and are then deleted, so an abandoned record cannot pin a stale status to the cockpit. `shell.qml` reads all live state from `seele-control status`. Now-playing rendering lives in the external repository's `media.js`, a plain JavaScript module shared by `shell.qml` and its Node test: it labels every player `<title> · <artist>`, falls back to the album so podcasts show their show name, and collapses the second MPRIS service Spotify's embedded Chromium registers for the same track by comparing track length before titles. The standalone package applies a librepods patch that adds a read-only JSON status command so AirPods component batteries can join that state without exposing the accessory's private pairing material; it carries that exact build through a passthru so its Home Manager service cannot fall back to the global package set. The Bluetooth panel also runs this machine as an audio receiver. Two things stand between a phone and that. iOS routes its output picker on the class a device advertises and never offers a Computer-class device as a speaker however complete its A2DP sink records are, so `nerv`'s adapter declares the Audio/Video major and Loudspeaker minor class and lets BlueZ derive the service bits from the profiles PipeWire actually registers. And PipeWire publishes a phone that streams here as an ordinary Bluetooth source node and links it to nothing, so `seele-bt-receiver` supervises one `pw-loopback` per connected Bluetooth source into whatever the current default output is; `setsid` makes that supervisor a process group leader, so turning the mode off retires every loopback with one signal instead of waiting for its next poll, and its capture streams carry `seele.role=bluetooth-receiver` so the recording indicator does not read a phone as a microphone in use. Receiver mode itself leaves discoverability alone, because a device this machine has already paired reaches it over ordinary page scan. Accepting a new one is the other half of one symmetric two-minute discovery window, the way a phone's Bluetooth screen behaves: the panel's search action runs `bluetooth_discovery_start`, which scans, makes the adapter discoverable under a timeout BlueZ enforces itself, and starts `seele-bt-agent`, a small D-Bus agent. Searching and answering share that one lifetime, because a scan that does not also answer leaves a phone unable to reach the machine at all, and two windows of different lengths would stop the spinner while the adapter was still open. Registering any agent is what lets a phone pair here — BlueZ rejects an incoming request outright when it has nobody to ask — and the agent's capability decides which association models it can then satisfy. `KeyboardDisplay` covers all of them: numeric comparison against a peer that can display, and passkey or PIN entry against one that cannot, which `DisplayYesNo` has to refuse, and a refused model is a pairing that simply fails. The agent draws nothing: it writes the pending request under `$XDG_RUNTIME_DIR/seele-shell/`, calls `seele-shellctl bluetooth-pairing` so the shell renders the exchange on the YubiKey prompt's card — six digits to compare, or a text field to type the peer's code into — and polls for the verdict the shell writes back through `seele-control bluetooth-pairing-answer`, matched by a single-use token. Pairing this machine starts runs through that same agent and prompt rather than a terminal, so both directions of pairing are one exchange. Accepting also marks the device trusted, because an untrusted device needs an agent to authorise every service it opens and none runs once the window closes. The agent owns the window's lifetime, so when it expires it rejects whatever is still on screen and restores the adapter itself, and it logs which model each remote picked, because that is invisible from anywhere else and is the first thing worth knowing when a pairing fails. `bluetooth_state` marks a device `source` when it advertises the A2DP Audio Source UUID and `streaming` while BlueZ reports an active media transport for it; the panel keeps one unified device list, ordered on pairing and name but never on connection state, which changes on its own and would pull a row out from under the pointer aimed at it, and reads `streaming` there, so a phone playing into the machine sits among everything else under the actions every row already has, and the receiver row above the search only counts them. On `nerv`, the OpenLogi feature installs its GUI and CLI, enables the upstream udev rules and `uinput`, and runs the HID++ agent as `seele-openlogi-agent.service`; the separate unit name prevents OpenLogi's mutable launch-at-login setting from rewriting Home Manager's service. `seele-control` samples `openlogi list` at most once every 30 seconds and adds every online Logitech device that reports a battery to the shared battery menu. Connection changes use the shell OSD and librepods notifications are suppressed. The bar's clock and date own a searchable world-clock picker and a Monday-first, ISO-week calendar; the expanded clock renders local time with seconds and every other zone through its current UTC offset at minute precision, while any number of persistent pins sort to the top of its list rather than adding bar entries. Calendar and ordering logic live in the external repository's shared `time.js` module, while `seele-clock` resolves IANA zones and common abbreviations against packaged tzdata without changing the system timezone. The click-away and AI cockpit surfaces stay mapped with empty input masks while idle so opening a panel under a stationary pointer cannot make Hyprland lose the next menu-bar press. Shell chrome comes from one token block at the top of `shell.qml` — a single radius matching Hyprland's window rounding, the bar metrics, and the hover, press, selection, and semantic tints — applied through the `PanelSurface` and `BarItem` components so panels, buttons, and menu-bar entries cannot drift apart. Opening a panel records its output in `overlayScreen`, and the OSD records its own in `osdScreen`, so a surface stays on the screen that opened it instead of following Hyprland's focused monitor when the pointer crosses an edge. The bar and the panels are one textured material: a `SurfaceWash` gradient under the content, a tiled grain film and edge highlight over it through `SurfaceGrain`, and translucent fills that `hl.layer_rule` blurs for every shell namespace except the wallpaper and the click-away catcher. `PanelSurface` is a `ClippingRectangle` because a plain `Rectangle` cannot clip that tiled image to its rounded corners. Bar entries fill the bar's full height so a pointer thrown at the screen edge still hits them, while only the pill inside is inset, and an open panel highlights just the entry on the screen it was opened from. The audio entry and both panel sliders adjust in five-point wheel steps through one locally batched update, while a middle click on the entry toggles output mute. The Control Center is the one panel that carries several modules at once: connectivity, camera, AirPods, output and microphone level, and now playing. Every module in it also keeps the menu bar entry and dedicated panel it had before, so a module lives in both places rather than moving between them. Its four-column grid leads with a full-width media card. A two-column connectivity card sits below it beside an equal-height Audio card with stacked horizontal output and microphone controls. Camera fills the short bottom row until connected AirPods split that row into two tiles. The connectivity card carries Wi-Fi, Bluetooth, and VPN rows. Each splits the interaction the way macOS does: the round knob owns the radio or selected private-network client while the rest of the row hands off to the panel that owns the devices behind it. The private networks still have their own module and `vpn` panel, so they can carry a menu bar entry of their own; that module acts on whichever client is connected or, failing that, the first one that could connect. Modules follow the same visibility rules as their menu bar entries, so AirPods appear only while they are connected. Placement is a module drag: `seele-control bar show/hide` records only the choices the user actually made in `bar.json`, `barModules` carries them through `status`, and `barModuleDefault` supplies the rest, so every module except VPN keeps the entry it shipped with. Dragging a module out of the panel onto the bar adds its entry and dragging an entry down off the bar removes it; the drag is the whole interface, with no placement marker on the module itself. Both surfaces are deliberately larger than what they paint: a Wayland client only keeps receiving pointer motion while the pointer stays inside the surface it pressed, so a drop target on a different layer surface loses the gesture halfway across. The Control Center reaches up over the bar and the bar reaches down the screen, each opening its input region — never its geometry, which would race the gesture — only while a drag is live, and the bar pins `exclusiveZone` to the strip it draws so the oversized surface reserves no extra space. The bar opens that region on the press rather than once the drag is recognised, because the region change costs a round trip the pointer would outrun. Two further constraints shape the removal gesture. A dragged entry has to stay mapped for the whole drag: previewing the removal by hiding it destroys the item holding the pointer grab and cancels the gesture, so the entry fades instead. And the entry opens its panel on release rather than on press, because a panel opened on the press sits on the Overlay layer directly in the path of the drag that follows, where it takes the pointer before the gesture can travel; the click-away catcher stands aside for the same reason while a bar entry is held. A modifier would have avoided the conflict, but a layer surface without keyboard focus never receives modifier state, so `mouse.modifiers` is always empty on the bar. `AudioLevelRow` remains the shared horizontal output/microphone slider in the Audio panel. `ControlLevel` gives the Control Center horizontal sliders with icon-only mute actions overlaid inside their tracks; the Audio card's empty area opens the full panel and owns module dragging without taking slider or mute input away from the controls. The Audio and connectivity cards retain their lateral insets while using smaller top, bottom, and inter-row gaps. `ConnectivityRow`, `ControlTile`, `MediaButton`, and `MediaTimeline` are the other module chrome. Control Center hover colors change immediately rather than animating a translucent card and its grain film through intermediate frames. Media selection for the single Control Center now-playing module is `media.js`'s `activePlayer`, which prefers whatever is playing and otherwise falls back to a paused player that still has a track. The wide media card follows iOS: large artwork on the left, track text and flat previous, play, and next controls on the right, and an MPRIS timeline along the bottom. `MediaTimeline` treats a duration longer than one year as the browser's live-stream sentinel and replaces seeking, the thumb, and timestamps with a bar split around `LIVE`. Menu bar players put the artwork before the label. The Camera panel uses the same stable name as its Control Center tile, and the Windows reboot action uses the same Power-panel button treatment as the ordinary session actions. Clicking that compact module or either now-playing menu bar entry opens the same larger media panel with artwork, transport controls, and an absolute draggable MPRIS timeline when the player reports seek, position, and length support. A bar label that carries arbitrary text — now playing, the focused window — goes through `BarLabel` rather than a bare `Text`: one glyph the primary font lacks pulls in a fallback whose taller line box moves an auto-sized, centred `Text` off the line its neighbours sit on, so the label anchors its baseline to an invisible reference in the primary font and the alignment cannot depend on the words. Every scrollable is a `SeeleListView` or `SeeleFlickable` rather than a bare `ListView` or `Flickable`, so one spring governs them all: Qt's default overshoot drifts long enough to read as lag rather than as feedback, so the flick decelerates hard and the rebound is short. `SlimScrollBar` replaces the platform indicator: it decides its own width and minimum handle size, sits above the view's delegates because an attached indicator is their sibling, and appears only while the pointer is over its popup and the content exceeds the viewport. It remains visible until an active thumb drag ends. `RoundedSource` gives an Image the shell's radius through `MultiEffect` masking, which Qt cannot do on the item itself. The world clock is not a curated list: `seele-clock` reads every named zone from tzdata's `zone1970.tab`, derives fixed UTC offsets from its `Etc/GMT` entries, names the countries from `iso3166.tab`, renders each country code as regional indicator letters for the flag, and samples January and July so both of a zone's abbreviations stay searchable. Bash's `printf` time format is a builtin, so several hundred zones cost no processes. The cockpit's `seele-os-session` opens Pi in the flake on workspace 9 with a briefing about this repository, then runs `nh os switch` and offers to record the change with a Pi-written subject line through `jj commit`; the terminal is interactive because the rebuild needs a sudo password. The grain tile itself is not committed: the external repository's `grain.js` writes a seeded 128px noise PNG with Node's zlib during the install phase, so the asset stays reproducible and the repository stays free of binaries. The network panel reads Tailscale's local status and Proton VPN's NetworkManager connection, owns their connect/disconnect actions, and opens an interactive client only when sign-in or location selection needs the user; credentials remain in the clients' own state. A Home Manager user service runs `tailscale systray`; clicking the Tailscale VPN card opens its StatusNotifier menu inside Seele Shell, while the card's switch still connects or disconnects. The same panel reports the OpenSSH service's live state and starts or stops it through PolicyKit; SSH remains limited to Tailscale and public-key authentication. Its speed test uses the packaged official Ookla CLI, accepts its license and GDPR terms noninteractively, selects from Ookla's nearby servers, and streams ping, download, and upload progress into the local gauges. The shell also consumes yubikey-touch-detector's Unix socket through its packaged watcher, keeping hardware-touch prompts in the OSD instead of the notification daemon. Mako keeps notification state and history but hides its own popup. Seele Shell watches notification D-Bus traffic and draws each current notification with the shell material, its action target, and an explicit close button. Mako expires nothing — `default-timeout` is zero and `ignore-timeout` keeps a sender from overriding that — so a notification stays current until it is dismissed and every entry in the panel is still actionable, which is only true while mako holds it. The popup owns its own lifetime instead: `notification_state` stamps each notification the first time it is seen, and the shell retires the toast ten seconds after that stamp, or at once when its close button is pressed, without touching what raised it. Its 24-hour history therefore holds only what was actually dismissed, and `max-history` is raised well past mako's default of five so a day's worth can fit. Rows size themselves to the notification: the panel and the history unfold every entry, a toast keeps one elided line and grows an unfold control only while `implicitWidth` exceeds the width it was given, and both surfaces take their height from the list's measured `contentHeight` rather than a fixed row count. A history entry stays a record because Mako can only invoke actions while the notification is current. Current and historical entries remain separate resident lists, and the panel keeps its opening height while either list changes, so switching views and dismissing an entry does not remap the layer surface. The webcam preview lives in a separate `CameraPreview.qml`, isolated from the main shell and loaded asynchronously only while its panel is open so it releases the device before a delayed detached preview launch; its viewport sits above the panel's decorative grain, camera labels strip v4l2's USB topology suffix, and a missing QtMultimedia backend cannot break the shell. The Camera settings action closes that preview, selects the camera's serial-backed OpenLogi key in OpenLogi's mutable config, and restarts its on-demand GUI so the MX Brio opens directly on its Camera tab. The wrapper extends `QML2_IMPORT_PATH` and `QT_PLUGIN_PATH` for that component. The package also ships a managed Vicinae extension for shell actions and live Hyprland keybinding search; the Home Manager feature links it into Vicinae's extension directory. Other raw package assets live in `_nixvim/` and `_spt-st/`; underscore paths are intentionally excluded from import-tree.

The audio device list is not just the sink and source nodes. A card whose profile is `Off` has no sink node at all, so enumerating nodes alone hides every output that is merely switched off — onboard analog and HDMI are the usual casualties, and the list collapses to whichever interface happens to be active. `control.sh`'s `audio_devices` therefore adds a second kind of entry, built from each `Audio/Device`'s `EnumProfile`, gated on the card having no sink already *and* the profile reporting `available: yes`; that gate is what keeps unplugged jacks and every `Pro Audio` variant out of the list. Those entries carry a `profile` index instead of a node name, and `seele-control audio-device <device> <profile>` switches the card with `wpctl set-profile` and then waits for the node PipeWire creates for it before making that the default — the sink does not exist at the moment of the click, so without the second step the choice only half-applies.

The microphone's mute is two mutes on most desktops, and `seele-mic-sync` makes them one. A USB microphone that gates itself — the Shure MV7+ does when its touch panel is tapped — publishes that as its USB Audio Class feature-unit mute, which ALSA exposes as an ordinary `Microphone Capture Switch` and the device announces on the status interrupt endpoint of its audio control interface, so the switch is an event source rather than something to poll. PipeWire owns none of it: `wpctl set-mute` on a source node applies a software mute inside the graph and leaves the device capturing, so the panel and the desktop each held half of one state — a tap silenced a call the desktop still showed as live, and unmuting in the desktop could not bring a panel-muted microphone back, because nothing in the graph held what was actually gating the signal. The daemon watches `alsactl monitor` and `pw-dump -m` together and moves each side to the other, which also carries the panel's LED, since it follows the same control. Two rules keep it honest. Every event is answered by reading the side that raised it rather than trusting the value the event carried, because `pw-dump -m` replays changes in order and a burst that collapses into one wake-up would otherwise settle on history; that also makes each write's echo compare equal to the state both sides were last agreed on, so neither side answers its own. And the switch wins when the node first appears, at startup and after a replug, because adopting the node's mute there would leave a microphone the user muted by hand reporting itself as live. A device-side change raises the desktop's own microphone OSD, which shares one level strip with the output OSD; `seele-shellctl microphone` is the action form, and is also what `XF86AudioMicMute` runs. The acknowledgement takes a different route from the action, because it is not asking for anything: `seele-shellctl microphone-state` carries the mute the daemon already established straight to the shell, where the ordinary `seele-control status` gather would have put its several hundred milliseconds — occasionally over a second — between the tap and the OSD for a value nobody needed to rediscover. The daemon also sends it without waiting, so a shell that is slow to answer, or not running, cannot delay the mute it is only being told about; the test drives the whole run against a shell that takes three seconds to reply and holds the sync to its ordinary latency. The microphone is named by USB vendor and product id, the one identity that survives a replug; its ALSA card, that card's capture switch, and its PipeWire node are all derived from it, and the daemon rescans quietly while it is unplugged. The external repository's `tests/mic-sync.sh` drives all of this against an ALSA card and a PipeWire graph made of files, whose stubs log every write rather than their current value, because the cases worth testing are the ones where a second change lands before the first has been read back.

Package directories are no longer discovered by custom `readDir` logic. A package exists because a dendritic leaf contributes it to `perSystem.packages`.

## Validation boundaries

The interactive rebuild abbreviations remain:

- NixOS: `nh os switch`
- Darwin: `nh darwin switch -H asuka`

They activate live state and are not validation commands. Use direct `nix flake`, `nix eval`, and `nix build` commands from the skill. Darwin Home Manager theme modules can force generated Darwin assets, so Linux evaluation may fail with a platform mismatch; validate the complete `asuka` closure on Darwin.
